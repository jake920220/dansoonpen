# 재발 조사용 로컬 진단 로그

v0.3.1부터 앱을 실행하면 자동 기록한다. 2026-09-08 강의 중 **전체 화면이 검은 회색으로 덮이고 Option+X·Option+Z 모두 반응하지 않은 현상**의 재발 원인을 구분하기 위한 기능이다. 원인 수정이나 재발 방지 완료를 의미하지 않는다.

## 저장 위치와 보관

- macOS: `~/Library/Logs/com.junhyun.my-brush/diagnostics/`
- Windows: `%LOCALAPPDATA%\com.junhyun.my-brush\logs\diagnostics\` (Windows 실기는 미검증)
- 최신 `diagnostics.jsonl`, 이전 `diagnostics.1.jsonl`–`diagnostics.3.jsonl`.
- 파일당 최대 1MiB, 로그 4개로 최대 4MiB. 새 실행에서도 이전 로그를 이어 보관하고, 크기 한도에 도달하면 가장 오래된 기록부터 교체한다. 여러 프로세스도 같은 파일 잠금으로 회전을 조정한다.
- `diagnostics.lock`은 쓰기 조정용 빈 파일이다. 진단 중 이 파일을 삭제하지 않는다.
- macOS 신규 파일은 사용자 전용 권한 0600으로 생성한다. 외부 전송이나 자동 업로드는 없다.

재발하면 발생 시각과 사용한 공유 앱을 알려주고, 가능하면 위 폴더의 JSONL 파일 4개를 보관한다. 앱을 여러 번 재실행하거나 오래 사용하면 오래된 구간이 교체될 수 있다. 강제 종료해도 이미 파일에 쓴 로그는 남지만, 마지막 대기열이나 기록 중인 줄까지 보존되는 것은 보장하지 않는다.

## 기록하는 항목

| 항목 | 확인 목적 |
| --- | --- |
| 버전·PID·세션 ID·시각·순번 | 실행 구간, 종료·재시작과 기록 생략 구분 |
| 등록한 전역 키 조합·등록 결과·수신·반복 억제·처리 시작 | 키가 앱에 도착했는지, 도착한 뒤 처리되지 않았는지 구분 |
| UI·트레이 명령 진입과 완료·성공 여부·소요 시간 | 마지막으로 진행된 명령과 정지 단계 파악 |
| 모드 전환의 입력 해제·창 표시·포커스 단계 | 창 활성화·뒤 앱 복귀 중 어느 부분에서 멈췄는지 확인 |
| 창 생성·이동·크기·배율·입력 허용·포커스·불투명 여부 | 새 창 증가, 잘못된 배치, 불투명 창 전환 구분 |
| 화면 구성 변경과 해시로 표시한 화면 식별값 | 모니터 선택·연결·배율 변화와의 연관 확인 |
| 네이티브 10초 응답 확인과 미응답 시간 | 메인 스레드가 멈춰도 별도 스레드에서 대기 상황 기록 |
| WebView 10초 생존 신호·Canvas 크기·배경 불투명 여부·오류 종류 | 네이티브와 WebView·Canvas 상태 비교 |
| 장면 revision·객체 개수·삭제 수신 | 삭제 명령 뒤 화면 데이터 갱신 여부 확인 |

일반 키 입력, 필기 선의 점·위치·색·본문, 입력한 텍스트, 화면 이미지, 공유 영상, URL, 오류 메시지·stack 원문은 기록하지 않는다. JS 오류는 고정된 종류와 상태 숫자만 기록한다.

## 부하와 실패 처리

- 디스크 쓰기는 전용 작업 스레드가 담당한다. UI는 최대 128개 대기열에 기다리지 않고 넣으며 가득 차면 기록을 생략한다. 다음 기록의 `dropped` 값으로 생략 수를 알 수 있다.
- WebView는 IPC 1개만 진행하고, 대기 이벤트는 종류별 최신 1개씩 최대 9개다. 같은 종류는 초당 최대 1회 전송하며 오류 폭주에서도 레이아웃 측정과 전송을 병합한다. 네이티브에서도 프런트엔드 기록 수와 숫자 범위를 제한한다.
- 포인터 이동이나 매 프레임을 기록하지 않는다. 정상 획 저장·펜 설정 명령은 실패하거나 250ms 이상 걸린 경우만 별도 명령 기록을 남긴다.
- 네이티브 응답 확인은 이전 요청이 끝나기 전 다음 요청을 쌓지 않는다. 응답 대기 중에도 별도 스레드가 10초마다 미응답 시간을 기록한다.
- 파일 쓰기나 로그 위치 접근이 실패하면 로깅을 중단하고 필기 기능은 계속 실행한다. 로그가 없다는 사실만으로 앱에 문제가 없었다고 판단하지 않는다.
- 종료 때 대기열 배출을 포함해 최대 300ms 기다린다. 전원 차단·강제 종료·OS/디스크 장애까지 기록 보존을 보장하지 않는다.

## 재발 시 해석 순서

1. `session.start`의 버전·PID와 마지막 `session.exit` 유무를 확인한다.
2. `shortcut.received`가 있고 `shortcut.action`이 없는지 확인한다. `ignored`의 capture/repeat, 등록 결과도 비교한다. 수신 기록이 없다고 다른 앱 충돌로 바로 확정하지 않는다.
3. `mode.step`·`command.begin/end`의 마지막 단계와 `native.probe_pending`을 비교한다.
4. 네이티브 응답은 계속되는데 필기 WebView의 heartbeat·state·scene 수신만 멈췄는지 확인한다. IPC 전달 자체의 정지, 숨겨진 WebView의 타이머 제한, 정상 종료도 함께 고려한다.
5. macOS native frame은 왼쪽 아래 원점의 AppKit points, 목표 모니터는 physical 좌표다. 배율·좌표계를 맞춰 비교한다. 창 변경 요청 직후 값은 OS 적용 전일 수 있으므로 `frameMayBePending` 및 후속 window event·probe를 함께 본다. `opaque`, `alpha`, `ignoresMouse`, `canBecomeKey`와 CSS `opaqueBackground`를 비교한다.
6. WindowServer/WebKit 합성 문제는 이 로그만으로 확정할 수 없으므로 해당 시각 macOS 통합 로그와 대조한다.

## 검증 범위

로그 회전·재시작 보존·독립 쓰기 핸들 간 회전·대기열 포화 시 무대기·종료 배출·파일 권한·필드 제한, 프런트엔드 오류 폭주·IPC 실패·타이머/이벤트 정리를 자동 검사한다. 사용자 증상을 자동 재현하거나 Windows 실제 창 동작을 검증한 것으로 표시하지 않는다.
