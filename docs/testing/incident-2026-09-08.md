# 화면공유 강의 중 오버레이 중첩 조사

조사일: 2026-09-08. 대상: 설치된 macOS arm64 My Brush v0.3.0, 소스 `d1dd2c2`.

**결론: 강의 중 발생한 시각적 중첩의 직접 원인은 미확정이다.** 현재 확보한 기록은 필기 창의 무한 생성이나 여러 My Brush 프로세스의 동시 실행을 뒷받침하지 않는다. 별도로 macOS 창 활성화 순서의 문제와 혼합 배율 계산의 위험을 찾았다. 이를 사건 원인이나 수정 완료로 취급하지 않는다.

앱을 재실행하거나 전역 키를 보내지 않았다. 사용자 설정과 실행 파일도 변경하지 않았다. 설치 실행 파일은 기존 v0.3 배포 ZIP의 실행 파일과 일치한다.

- 이전 `v0.3-mode-trace.log`는 개발 중 자동 검사 기록이다. 이번 강의의 모드 전환 기록으로 사용하지 않았다.

## 소스와 검사로 확인한 내용

### 같은 화면에서 창이 계속 생성되는 경로

`src-tauri/src/lib.rs`의 `ensure_overlay`는 화면 ID로 고정된 창 label을 만들고 기존 창을 재사용한다. macOS 명령은 메인 스레드와 상태 mutex로 직렬화된다. 전역 키의 반복 Pressed 이벤트도 키를 놓기 전까지 억제한다. 같은 화면의 반복 진입만으로 창이 누적되는 원인은 찾지 못했다.

연결이 끊긴 화면의 창은 숨기고 보관하므로, 화면 ID가 계속 바뀌는 상황에서는 숨겨진 WebView가 남을 여지가 있다. 이번 로그에서는 그런 생성 증가를 확인하지 못했다.

### 비활성 창을 활성화하려는 순서

`change_mode`는 `release_inputs`로 창을 focusable=false로 만든 다음 `show`, 그 뒤 focusable=true와 명시적 focus를 호출한다. 설치된 tao 0.35.3의 macOS `set_visible(true)`는 `makeKeyAndOrderFront`를 사용한다. 따라서 아직 키 창이 될 수 없는 상태에서 활성화를 요청하며, 로그의 경고와 일치한다. 화면 갱신에서도 비활성 필기 창에 `show`를 호출한다.

이 순서 문제는 확인했지만, 정상적인 그리기 진입 때도 경고를 만들 수 있다. 경고 자체가 시각적 중첩의 원인이라는 증거는 없다. 후속 수정은 비활성 표시와 입력용 활성화를 분리하고 실제 앱의 포커스 복귀를 검증해야 한다.

### 서로 다른 화면 배율에서 위치·크기 계산

현재 코드는 목표 화면의 physical 위치·크기를 Tauri에 전달한다. 설치된 tao의 변환은 현재 창의 배율을 사용한다. 두 배율이 다르면 의도한 logical 위치·크기와 값이 달라질 수 있다.

현재 화면 구성의 숫자를 이용한 예시: 목표 Retina 화면의 physical 위치 (5120, 968), 크기 2940×1912, 배율 2를 현재 배율 1인 창에 전달하면, 변환 결과가 목표 logical 위치 (2560, 484), 크기 1470×956과 다르다. 실제 dpi 0.1.2 변환을 사용한 별도 프로그램으로 계산 차이를 확인했다. 목표 배율로 변환하는 후보 방식은 12개 산술 사례를 통과했다.

이는 실제 창 배치·화면공유 재현 검증이 아니다. 사건 중 Retina 화면을 선택하거나 배율이 바뀌었다는 증거도 없어 직접 원인으로 확정하지 않는다.

### 단축키 충돌 가능성

저장된 단축키는 그리기 ⌥Z, 전체 삭제 ⌥X다. 사용 중인 global-hotkey 라이브러리는 Carbon `RegisterEventHotKey`에 옵션 0을 전달한다. 설치된 Apple SDK의 CarbonEvents.h는 비독점 등록에서 여러 앱이 같은 키 조합에 알림을 받을 수 있다고 설명한다. 따라서 등록 성공만으로 다른 앱과의 충돌이 없음을 보장할 수 없다.

다만 당시 어떤 앱이 같은 키에 반응했는지, 어떤 키가 눌렸는지는 현재 기록에 없다. 트레이 메뉴 가속키와 전역 키 콜백이 실제로 한 번의 물리 입력에 함께 호출되는지도 미검증이다. 기본 키를 추측으로 바꾸지 않았다.

### 그리기·커서 렌더링

Canvas는 매 렌더 전에 전체 비트맵을 지우고 장면을 다시 그린다. 커서 강조는 고정된 두 DOM 요소와 이전 것을 취소하는 단일 애니메이션으로 구성된다. 관련 기존 프런트엔드 테스트 14개를 통과했다.

My Brush 자체에는 데스크톱 화면을 캡처하고 다시 재생하는 코드가 없다. 공유 미리보기의 반복 반사나 OS 합성 잔상은 다른 가설이며, 단위 테스트로 배제할 수 없다.

## 원인 확정에 필요한 정보

1. 겹쳐 보인 것이 도구막대·앱 창인지, 선·색·잔상인지, 공유 화면 전체가 반복된 것인지.
2. 사용한 공유 앱과 문제가 본인 모니터에서도 보였는지, 수강생의 수신 화면에서만 보였는지.
3. 직전 키, 전체화면/Spaces 이동, 모니터 선택·배율 변경 여부.

그 뒤 동일 조건의 짧은 재현에서 명령 출처, 창 ID·실제 frame·배율, 모니터 변경만 제한된 로그로 기록하면 창 생성·위치 오류·시각 합성 문제를 구분할 수 있다. 강의 텍스트나 화면 영상은 진단 로그에 필요하지 않다.

## 후속 증상 확인과 진단 기능

준현님 추가 설명: **전체 화면이 검은 회색 오버레이로 덮였고, Option+X로도 닫히지 않고 Option+Z로도 상태가 바뀌지 않았다.** 도구막대가 여러 개 생긴 것으로 단정하지 않는다. 공유 앱·직전 화면 전환은 아직 미상이다.

요청에 따라 v0.3.1에 [로컬 진단 로그](diagnostics.md)를 추가한다. 네이티브 단축키 도착·명령 처리·창 속성·메인 스레드 응답과 WebView 생존 신호·Canvas 상태를 분리해 기록한다. 원인을 가정한 포커스·배율 수정이나 자동 강제 복구는 이번 변경에 포함하지 않는다.
