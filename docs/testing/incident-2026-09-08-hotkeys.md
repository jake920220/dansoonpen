# 간헐적 그리기 단축키 무반응 조사

## 조사 범위

준현님이 “중간중간 단축키를 눌러도 그림 모드로 바뀌지 않는다”고 보고한 후, v0.3.1의 실제 사용 로그를 조사했다. **원인은 미확정이다.** 수신한 단축키의 처리 성공과 사용자가 누른 모든 키의 정상 동작은 구분한다.

- 일시: 2026-09-08 12:58:07.220–13:44:07.214, KST.
- 세션: `1788839887220-66259`, 앱 버전 `0.3.1`.
- 진단 기록 4,000개, 순번 1–4,000 연속, `dropped=0`, 정상 종료 기록 존재.
- 원본 보존: Git 제외 경로 `artifacts/incident-20260908-hotkeys/`에 JSONL 2개와 해당 PID의 macOS 통합 로그를 복사/추출했다. `audit-summary.json`에 집계와 SHA-256을 기록했다. 원본 로그는 변경하지 않았다.
- 이번 조사에서 앱 실행·재시작·키 입력·설정 변경은 하지 않았다. 브라우저 테스트를 네이티브 검증으로 사용하지 않았다.

## 발견한 이상 징후

### 13:29:10 포커스 이탈과 WebView 상태 불일치

| 시각 (KST) | 기록 |
| --- | --- |
| 13:29:08.215 | Alt+Z 수신 후 그리기 진입 시작 (`#2805`부터) |
| 13:29:08 이후 | `focused=true` 및 네이티브 probe에서 key=true·입력 허용 확인 |
| 13:29:10.683 | 모드는 draw인 상태에서 네이티브 `focused=false` (`#2826`). 앞선 모드 종료 명령 없음 |
| 13:29:11.618 | Alt+X 수신·삭제·interact 전환 처리 (`#2827`부터) |
| 13:29:14.796–13:29:54.815 | WebView heartbeat 5회에서 interact인데 `document.hasFocus()`는 true. 이 구간 네이티브 probe는 key=false·입력 통과로 일치 |
| 13:29:58 이후 | 다음 Alt+Z도 수신되어 draw 진입 및 포커스 확보 |

포커스가 빠진 계기는 현재 로그에 없다. 다른 앱/시스템 UI로 정상 전환했을 가능성과 창 포커스 문제를 구분할 수 없다. WebView의 포커스 값만 실제 키 수신 대상으로 신뢰하면 안 된다는 증거다. 해당 구간의 Alt+X와 다음 Alt+Z는 처리됐으므로 이 불일치가 보고된 무반응의 원인이라는 결론은 내리지 않는다.

### macOS 포커스 경고 72회

동일한 필기 창에서 `makeKeyWindow` 요청 시 `canBecomeKeyWindow`가 NO라는 경고가 72회 있다. `change_mode`의 입력 해제 → `show()` → focusable 활성화 → focus 요청 순서가 이 경고를 설명한다. 그러나 이번 세션의 그리기 진입 72회 모두 이후 포커스를 얻었으므로 **경고가 곧 전환 실패를 의미하지 않는다.** 이전 검토에서 확인한 창 표시/포커스 순서 개선 후보를 유지한다.

### 메모리 압박 및 설정 WebView 경고

- 13:22:11에 WebKit 메모리 압박 처리 메시지 2개. 해당 시각의 메모리 사용량이나 어느 앱이 압박을 일으켰는지는 이 기록으로 알 수 없다. 필기 WebView heartbeat는 계속됐다.
- 설정 WebView (`PID 66278`, page 8)의 레이어 volatile 전환 지연 경고가 반복됐다. 필기 WebView (`PID 66334`)의 멈춤으로 해석하지 않는다.
- 조사한 해당 PID 통합 로그에 `unresponsive`, `processDidTerminate`, `GPUProcessProxy::gpuProcessExited` 메시지는 없었다. OS 장애 전체를 배제하는 증거는 아니다.

## 남은 판단과 다음 조사

1. **OS에서 앱까지 전달되지 않은 키 입력은 현재 로그에 남지 않는다.** `dropped=0`은 로깅 대기열에서 생략하지 않았다는 뜻이며, 모든 물리 키 입력을 받았다는 뜻이 아니다. 전역 단축키 충돌을 확정하거나 배제할 수 없다.
2. 현재 고정 버전 `global-hotkey 0.8.0`은 macOS `RegisterEventHotKey` 옵션 0을 사용한다. 로컬 SDK `CarbonEvents.h`의 비독점 등록 규정상, 등록 성공만으로 다른 앱과 충돌하지 않는다고 보장할 수 없다.
3. 실제 무반응 시각과 당시 앱/메뉴/전체화면 상태를 위 기록과 대응하는 것이 우선이다. 이번에 확인한 13:29 포커스 이탈이 사용자가 체감한 시점과 같은지는 미확인이다.
4. 후속 재현에서는 단축키 직후 짧은 간격의 실제 창 입력·포커스 상태와 현재 전면 앱, 포인터가 대상 화면에 있는지를 확인한다. 현재 10초 probe는 그 사이의 짧은 장애를 놓칠 수 있다. 원시 키 입력이나 강의 내용을 기록하지 않는다.

제품 동작이나 실행용 앱은 이번 조사에서 변경하지 않았다. 위 포커스 현상, 단축키 미수신 가능성, 앞선 검은 회색 화면 사건의 원인을 각각 미확정으로 유지한다.
